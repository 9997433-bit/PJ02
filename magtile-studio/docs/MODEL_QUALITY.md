# 模型质量承诺: 逐片零差错 (Model Quality)

本文档定义 MagTile Studio 内容库的**逐片零差错**质量承诺, 以及支撑这一承诺的自动化检查体系。

## 0. 为什么需要"逐片零差错"

MagTile Studio 的教程是**逐片摆放**的: 每一步告诉用户"拿起哪几片、放在哪里"。内容库规划规模为 500 个模型 (见 [CONTENT_STRATEGY.md](CONTENT_STRATEGY.md)), 按平均 80 片/模型估算, 就是 **4 万次逐片放置指令**。任何一片错了——重复放置、引用幽灵片、顺序颠倒、高亮还没放的片、成品和教程对不上账——用户就会在真实桌面上卡住: 手里拿着一片不知道放哪, 或者照着高亮找一片根本不存在的"参照物"。

人工审 500 个模型 × 每模型几十步是不可能完成的任务, 因此**每一条承诺都必须有对应的自动化检查**, 全部注册进 CTest 与 `tests/run_full_qa.sh`, 任何一条不满足即拒绝入库。

## 1. 承诺清单与检查归属

| # | 承诺 | 自动化检查 | 归属 |
| --- | --- | --- | --- |
| P1 | 每片磁力片 id 全模型唯一 | `test_step_assembly.py` 检查 1 | 逐步装配质检 |
| P2 | 每片在教程中**恰好出现一次** (不重复、不遗漏) | 检查 2 / 3 / 5 | 逐步装配质检 |
| P3 | 每步 `tiles_to_add` 全部是**新片** (未被之前步骤放过) | 检查 2 / 3 | 逐步装配质检 |
| P4 | `highlight_tiles` 只引用**已放置**的片 | 检查 4 | 逐步装配质检 |
| P5 | 第 N 步后的累计状态 == 第 1..N 步 `tiles_to_add` 的并集 | 检查 2~5 联合保证 | 逐步装配质检 |
| P6 | `final_assembly` == 全部步骤累计 (无孤儿、无幽灵) | 检查 5 / 6 | 逐步装配质检 |
| P7 | 每步新片与已放结构**空间连续** (磁力边吸合或接地) | 检查 7 | 逐步装配质检 |
| P8 | 步骤序号从 1 连续递增, 无跳号无重号 | 检查 8 | 逐步装配质检 |
| P9 | 每个**中间状态**物理成立 (R1~R8) | `magtile_app validate` | 物理校验器 |
| P10 | 全库无"换皮克隆"模型 (结构签名相似度 ≤ 0.85) | `test_library_uniqueness.py` | 库级唯一性 |

P1~P8 由 `tests/test_step_assembly.py` 静态保证 (纯数据层, 不依赖 C++ 构建产物, 秒级跑完全库); P9 由 C++ 物理校验器保证; P10 由 `tests/test_library_uniqueness.py` 保证。三者与既有关卡 (`test_model_logic.py`、`test_tutorial_integrity.sh`、`test_anti_trivial.py`) 互为冗余防线: **同一条承诺允许被多个关卡重复把守, 但不允许任何一条承诺没有关卡把守。**

## 2. 承诺的精确定义

### P1 片 id 唯一

`final_assembly` 中任何两片的 `id` 不得相同。id 是教程、高亮、进度存档、渲染选中的**唯一外键**, 一旦重复, "高亮 w_3" 这类指令就有二义性。

### P2 / P3 每片恰好放置一次, 每步只放新片

把全部步骤的 `tiles_to_add` 顺序展开, 得到的序列必须**恰好**是 `final_assembly` id 集合的一个排列:

- 某 id 出现两次 (无论同一步内还是跨步骤) → 用户第二次会发现"这片已经在结构上了";
- 某 id 在第 K 步出现而它已在第 J < K 步放过 → 顺序错乱, 教程叙事崩坏;
- 某 id 从未出现 → 成品里有"从天而降"的孤儿片。

### P4 高亮只指向已放置的片

`highlight_tiles` 的语义是"**参照物**": 本步新片要贴着谁放。参照物必须在**本步开始之前**就已经在结构上, 否则教程界面会高亮一片桌面上还不存在的空气。注意: 本步 `tiles_to_add` 里的片也不算——它们是本步的主角, 不是参照物。

### P5 累计状态可复算

第 N 步完成后的结构状态没有独立字段, 而是由"第 1..N 步 `tiles_to_add` 的并集"**推导**出来。P2/P3 保证并集无重复, P4 保证高亮引用落在并集内, 于是任何一步的中间状态都可以从模型 JSON 确定性重建——渲染器、教程引擎、物理校验器三方复算的状态**必然一致**。

### P6 成品与教程对账

`final_assembly` id 集合 == 全部 `tiles_to_add` id 集合 (严格集合相等):

- 成品有而教程没有 → **孤儿片** (orphan): 用户搭完教程发现成品图里多出几片;
- 教程有而成品没有 → **幽灵片** (ghost): 教程让用户放一片在成品数据里不存在的片, 位置/旋转/颜色全部无从谈起。

同时, 每片的 `type` 必须在 `data/tile_catalog.json` 形状目录中登记, `position` / `rotation` 必须是有限数值 (无 NaN/Inf)——步骤只存 id, 片的全部几何数据以 `final_assembly` 为唯一权威来源, 这份数据本身必须完好。

### P7 空间连续性

每一步的每片新片, 在放下的那一刻必须满足以下二者之一:

1. **接地**: 存在顶点 `z ≤ ground_tolerance` (0.02, 与 C++ `PhysicsConfig` 一致);
2. **磁力吸合**: 至少一条磁力边与**已放置结构** (含本步内先放的片) 的某条磁力边完全贴合 (端点两两重合, 容差 `connect_tolerance` = 0.02)。

这是物理规则 R7a (放下瞬间必须有依托) 的纯 Python 复算, 采用与 C++ 完全一致的几何约定 (旋转 R = Rz·Ry·Rx, 本地顶点位于 XY 平面, 磁力边按 `magnet_edges` 索引)。地台层 (第 1 步或后续新开的接地结构) 走接地分支, 其余片必须吸在已有结构上——**不允许"隔空搭"**: 新片飘在离已有结构 3 格远的地方, 静态成品也许合法, 但教程叙事上是断裂的。

### P8 步骤序号连续

`step_number` 必须为 1, 2, 3, … 严格连续。跳号 (1, 2, 4) 会让"共 N 步, 当前第 K 步"的进度显示与实际不符; 重号会让进度存档 (按步骤号记录) 产生二义性。

### P9 每个中间状态物理成立 —— 为什么能防"搭到一半塌了"

物理校验器 (R1~R8, 见 [PHYSICS_RULES.md](PHYSICS_RULES.md)) **不只校验最终成品**, 而是对**每一个教程步骤完成后的中间状态**逐一执行全部静态规则, 并按步骤顺序逐片模拟放置 (R7):

- 成品合法 ≠ 中间状态合法。典型反例: 先挑出屋檐再补斜撑——成品有斜撑当然稳, 但挑檐完成、斜撑未装的那一步是超预算悬臂, 实搭必掉。R6 对第 N 步中间状态的校验正是拦这个;
- 悬挂链 (R5)、重心 (R4)、连通性 (R1/R2) 同理: 每步完成后都必须独立成立;
- R7 更进一步, 逐片检查"放下的瞬间": 依托是否存在 (R7a)、手是否伸得进去 (R7b)。

因此"搭到一半塌了"在本体系下不是运营事故, 而是**入库前必然被拦截的校验失败**。这也是 P7 (空间连续性) 与 P9 (中间态物理) 的分工: P7 是纯数据层的快速静态检查 (不依赖构建产物, 全库秒级), P9 是完整静力学预算校验 (承重/力矩/可达), 两道防线互为冗余。

### P10 跨模型唯一性

500 个模型的价值在于**每个模型结构逻辑各异** (CONTENT_STRATEGY.md 第 2 节)。换色、镜像、微调尺寸的"换皮克隆"会稀释整个内容库。判定采用结构签名相似度 (CONTENT_STRATEGY.md 5.2 节):

```
sim = 0.6 × WL 连接图指纹 Jaccard + 0.25 × 片形直方图余弦 + 0.15 × 步骤节奏 DTW
```

- **WL 指纹**: 从 `final_assembly` 构建磁力连接图 (节点 = 片形, 边 = 相对姿态类别: 共面 / 90° 折 / 其他角度), 跑 3 轮 Weisfeiler-Lehman 迭代取标签多重集。对颜色、全局平移/旋转、id 命名天然不敏感——换色与镜像翻版在算法层面自动同构;
- **判定**: 任意一对模型 sim > 0.85 → FAIL (克隆, 拒绝入库); 0.70 < sim ≤ 0.85 → WARN (边界案例, 送人工比对, 结论记入 `content_meta.curator_review.boundary_case_note`);
- **主题/技法拥挤度**: 同一主题 (`content_meta.series`) + 同一主技法 (`technique_tags.primary`) 的模型超过 2 个 → WARN, 提示内容规划审视该组合是否过度开采。

## 3. 规模化方案: 500 个模型的 CI

### 3.1 分层执行策略

| 层 | 检查 | 复杂度 | 500 模型预算 |
| --- | --- | --- | --- |
| L1 数据层 | `test_step_assembly.py` (P1~P8) | 每模型独立, O(片数 × 已放片数) 几何比对 | 单进程 < 30s, 可按模型分片并行 |
| L2 物理层 | `validate_*` / `tutorial_*` (P9) | 每模型独立的 CTest 用例 | `ctest -j N` 天然并行 |
| L3 库级 | `test_library_uniqueness.py` (P10) | 两两比对 O(N²), 500 模型 = 124,750 对 | 签名逐模型缓存后, 两两比对为纯字典运算, 毫秒级/对 |

关键设计决策:

1. **每模型一个 CTest 用例** (已实现): `CMakeLists.txt` 对 `data/models/*.json` GLOB 注册 `validate_<模型名>` / `tutorial_<模型名>`, 新增模型零手工登记。500 模型 = 1000+ 个独立用例, `ctest -j $(nproc)` 直接吃满核心数, 且**失败精确定位到模型**——不会出现"全量脚本挂了, 不知道是 500 个里的哪一个";
2. **数据层检查不依赖构建产物**: `test_step_assembly.py` / `test_library_uniqueness.py` 只读 JSON, 内容作者在本地不配 C++ 工具链也能跑, 提交前自查成本为零;
3. **库级 O(N²) 的成本控制**: 相似度的三个分量中, WL 指纹计算 (需要几何吸合判定) 是大头, 但它**每模型只算一次**; 两两比对阶段只做多重集 Jaccard / 直方图余弦 / DTW, 均为轻量运算。500 模型全量比对在单机分钟级以内。若未来超出, 按 CONTENT_STRATEGY 5.2 的设计将指纹登记进 `data/uniqueness_index.json`, 增量 PR 只比对"新模型 × 全库", 即 O(增量 × N);
4. **批量报告**: 两个 Python 关卡对每个模型输出一行 `[PASS]/[FAIL] 模型名: 统计摘要`, 失败时给出**人类可读的差异明细** (哪一步、哪一片、期望什么、实际什么), 结尾输出全库汇总。CI 日志按模型名可 grep, 失败模型清单直接可以贴进 issue。

### 3.2 增量与全量

- **PR 级** (增量): 修改了哪些模型 JSON, 就跑哪些模型的 L1/L2 + 新模型对全库的 L3 比对;
- **主干级** (全量): `tests/run_full_qa.sh` 每日全量跑 L1+L2+L3, 防止参数调整 (如物理预算收紧) 造成的存量模型回归;
- **失败即阻断**: 任何 FAIL 阻断合入。WARN 不阻断, 但按 PHYSICS_RULES.md 第 6 节须逐条书面确认。

## 4. 检查清单速查 (内容作者自查用)

提交新模型前, 在仓库根目录执行:

```bash
python3 tests/test_step_assembly.py data/models          # P1~P8: 逐步装配质检
python3 tests/test_library_uniqueness.py data/models     # P10: 全库唯一性
python3 tests/test_model_logic.py data/models            # 粒度/中文/难度/BOM
python3 tests/test_anti_trivial.py data/models           # 反平凡
build/magtile_app validate data/models/<新模型>.json --data-dir data   # P9: 物理
```

或一键全量: `tests/run_full_qa.sh`。全绿即满足"逐片零差错"承诺的机器可验部分; 难度 4+ 模型另需实物复核 (见 [BUILD_VERIFICATION.md](BUILD_VERIFICATION.md))。
